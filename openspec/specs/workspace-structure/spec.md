## Requirements

### Requirement: Repository hosts an Nx classic integrated monorepo at its root

The repository SHALL contain an Nx classic integrated monorepo whose configuration files (`nx.json`, `package.json`, `tsconfig.base.json`, the ESLint configuration, the workspace lockfile) live at the repository root. The monorepo SHALL be split into `apps/` (deployable applications) and `libs/` (shared libraries) directories at the root.

#### Scenario: Root contains the Nx configuration files

- **WHEN** an operator lists the repository root
- **THEN** `nx.json`, `package.json`, `tsconfig.base.json`, and the ESLint configuration file generated by the preset are all present at the root level
- **AND** the directories `apps/` and `libs/` are both present at the root level

#### Scenario: Pre-existing repository content is preserved

- **WHEN** the scaffold is complete
- **THEN** `docs/`, `openspec/`, `visual-design-prototype/`, `CLAUDE.md`, and `.git/` are still present at the repository root with their content unchanged

### Requirement: The Angular application is named `lightmatters`

The monorepo SHALL contain exactly one deployable Angular application named `lightmatters`, located at `apps/lightmatters`, generated with SCSS styling and the esbuild bundler. The companion end-to-end test project SHALL be located at `apps/lightmatters-e2e`.

#### Scenario: The app is generated at the expected location

- **WHEN** an operator inspects `apps/`
- **THEN** `apps/lightmatters/` and `apps/lightmatters-e2e/` exist and are registered as Nx projects

#### Scenario: The app uses SCSS and esbuild

- **WHEN** an operator reads the `lightmatters` project configuration
- **THEN** the build target uses the esbuild-based Angular builder
- **AND** component styles default to SCSS

### Requirement: Three foundational libraries exist

The monorepo SHALL contain the following libraries, generated empty at scaffold time and ready to receive future code:

- `libs/design`
- `libs/engine`
- `libs/physics`

#### Scenario: Each foundational library is a registered Nx project

- **WHEN** an operator runs `nx show projects --tui=false`
- **THEN** the output includes `design`, `engine`, and `physics` alongside `lightmatters` and `lightmatters-e2e`

### Requirement: Projects carry scope tags

Every project in the workspace SHALL be tagged with a single `scope:*` tag that identifies its architectural role:

- `apps/lightmatters` and `apps/lightmatters-e2e` → `scope:app`
- `libs/design` → `scope:design`
- `libs/engine` → `scope:engine`
- `libs/physics` → `scope:physics`

#### Scenario: An untagged project would fail review

- **WHEN** a project's configuration is read
- **THEN** it has at least one `scope:*` tag from the allowed set

### Requirement: Module boundaries are enforced via ESLint

The workspace SHALL configure `@nx/enforce-module-boundaries` to enforce the dependency rules defined in `docs/architecture.md`:

| Tag                  | May depend on                                                          |
|----------------------|------------------------------------------------------------------------|
| `scope:app`          | everything                                                             |
| `scope:feature`      | `scope:design`, `scope:engine`, `scope:primitive`, `scope:physics`     |
| `scope:chapter`      | `scope:engine`, `scope:primitive`, `scope:physics`, `scope:design`     |
| `scope:primitive`    | `scope:engine`, `scope:physics`, `scope:design`                        |
| `scope:engine`       | `scope:design`                                                         |
| `scope:design`       | (nothing — leaf)                                                       |
| `scope:physics`      | (nothing — leaf)                                                       |

The rule SHALL include entries for `scope:chapter`, `scope:primitive`, and `scope:feature` even though not all such projects may exist yet, so future generators can produce projects with those tags without requiring an ESLint config edit.

#### Scenario: A forbidden cross-scope import fails lint

- **WHEN** a file in `libs/engine` attempts to import from `libs/physics`
- **AND** an operator runs `nx lint engine --tui=false`
- **THEN** the lint command fails with an `@nx/enforce-module-boundaries` violation

#### Scenario: An allowed cross-scope import passes lint

- **WHEN** a file in `libs/engine` imports from `libs/design`
- **AND** an operator runs `nx lint engine --tui=false`
- **THEN** the lint command succeeds

### Requirement: Build, lint, and test targets succeed on the scaffolded app

The scaffolded `lightmatters` application SHALL pass its `build`, `lint`, and `test` targets without code changes after scaffolding completes.

#### Scenario: Build succeeds out of the box

- **WHEN** an operator runs `nx build lightmatters --tui=false`
- **THEN** the command exits with status 0 and produces a build output directory

#### Scenario: Lint succeeds out of the box

- **WHEN** an operator runs `nx lint lightmatters --tui=false`
- **THEN** the command exits with status 0

#### Scenario: Tests succeed out of the box

- **WHEN** an operator runs `nx test lightmatters --tui=false`
- **THEN** the command exits with status 0

### Requirement: Tailwind v4 is wired into the `lightmatters` app via PostCSS

The `lightmatters` app SHALL use Tailwind v4 as its CSS utility layer, configured via the `@tailwindcss/postcss` PostCSS plugin. The app's global stylesheet entry SHALL be a `.css` file (not `.scss`) so PostCSS can handle `@import "tailwindcss";` directly. The stylesheet SHALL declare `@source` directives for every workspace library that contains templates with Tailwind classes.

#### Scenario: Tailwind packages are installed

- **WHEN** an operator reads `package.json`
- **THEN** `tailwindcss` (v4+) and `@tailwindcss/postcss` (v4+) appear under `devDependencies`

#### Scenario: PostCSS config registers the Tailwind plugin

- **WHEN** an operator reads `apps/lightmatters/.postcssrc.json`
- **THEN** the file declares `@tailwindcss/postcss` under `plugins`

#### Scenario: Global stylesheet imports Tailwind and scans the libs

- **WHEN** an operator reads `apps/lightmatters/src/styles.css`
- **THEN** the file's first non-blank line is `@import "tailwindcss" source("./app");`
- **AND** the file contains a `@source "../../../libs/design/src";` directive
- **AND** the file contains a `@source "../../../libs/engine/src";` directive
- **AND** the file contains a `@source "../../../libs/features/landing/src";` directive

#### Scenario: Build produces non-empty styles bundle

- **WHEN** an operator runs `nx build lightmatters --tui=false`
- **THEN** the build succeeds
- **AND** the emitted `styles-*.css` bundle contains the Tailwind preflight layer (size > 0)

### Requirement: Nx invocations in non-interactive contexts pass `--tui=false`

Every `nx` invocation issued by automation (agents, scripts, CI, documentation examples) SHALL include the `--tui=false` flag. Human-interactive invocations from a real terminal are exempt.

#### Scenario: An agent runs an Nx command

- **WHEN** an agent invokes any `nx` command
- **THEN** the command includes `--tui=false`

#### Scenario: A documentation example shows an Nx command

- **WHEN** project documentation gives an example `nx` invocation
- **THEN** the example includes `--tui=false`
